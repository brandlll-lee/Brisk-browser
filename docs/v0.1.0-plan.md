## 1. TL;DR

Brisk V0.1.0 是一个**极薄的、跨平台的、原生 MCP 化的 Chrome 控制层**。它做且只做这四件事：

1. **以 Node.js daemon 形式连接用户已运行的 Chrome**（通过 CDP WebSocket），不启动自己的浏览器。
2. **以 MCP server 形式（同时支持 stdio 和 Streamable HTTP transport）对外暴露 37 个浏览器原语工具**，让 Claude Code / Cursor / Cline / Codex / Continue 等任何 MCP 客户端都能直接驱动浏览器。
3. **提供 Skill 自学习机制**——Agent 遇到反直觉的网站行为时，可以主动调用 `write_skill` 工具把经验沉淀成 markdown；下次访问同域名时这些 skill 自动作为 prompt 注入。
4. **为未来路线预留两个关键扩展点**：(a) AI Agent 大脑挂接（V0.2 接 ai-sdk），(b) Chromium fork 嵌入（V0.3 抄 BrowserOS 的 server_manager.cc 模式，让 Chromium 进程直接 spawn 我们的 daemon）。

**不做**：Agent 大脑、AI SDK 集成、Chromium 编译、UI、用户产品功能（书签 / 历史 / SOUL.md 等）。这些是 V0.2+ 的事。

**技术栈**：Node.js 24 LTS · TypeScript 5.x strict · Zod 4 · `@modelcontextprotocol/sdk` v1.x · `ws` (CDP WebSocket) · Hono + `@hono/node-server` (HTTP) · 原生 `node:net` (跨平台 IPC) · pnpm workspaces · Biome (lint+format) · Vitest (单元测试)。

**核心信条**："**LLM 越强，Harness 越薄**" — 不在 Harness 里塞 selector hunt、retry 框架、DOM 树扁平化等 framework 操作。截图 + 坐标点击是默认范式，DOM/JS 是兜底。

## 2. 项目愿景与边界

### 2.1 长期愿景（V1.0 远景）

Brisk 是一个 AI 原生浏览器，对标 BrowserOS、Atlas、Comet、Dia，但要做得**比它们更彻底**：

- 不只是"装个 AI 侧边栏"，而是**让 AI Agent 成为浏览器的一等公民**（地址栏即自然语言入口、tab strip 即 agent 任务、bookmark 即 skill）。
- 不只是"接外部 LLM"，而是**本地 + 云双形态**（用户能用 Ollama / LM Studio 跑本地模型，也能接 ChatGPT/Claude/Gemini）。
- 不只是"控制浏览器"，而是**让浏览器学会自己**（每次失败都沉淀 skill，越用越聪明）。

### 2.2 V0.1.0 的边界

| | 做 | 不做 |
|---|---|---|
| 浏览器控制 | CDP 直连真实 Chrome / Edge / Brave | 启动/编译/分发自家浏览器 |
| 协议 | MCP stdio + Streamable HTTP | 任何专有协议 |
| 工具 | 37 个浏览器原语（对齐 browser-harness） | Agent 大脑 / 任务编排 / 多步推理 |
| Skill | 跨域名 + 跨 session 的 markdown skill 存储 + 自学习 | 自动 fine-tune / RL |
| 集成 | 任何 MCP 客户端 | 自家 UI / 自家 chat |
| 平台 | Windows + macOS + Linux | 移动端 |
| 浏览器 | Chrome / Edge / Brave / Chromium / Helium | Firefox（无 CDP） |
| 远程 | Browser Use Cloud（V0.1.1） | 自家云 |

### 2.3 不做的清单（防止 V0.1.0 范围蔓延）

显式声明 V0.1.0 **不**包含以下内容（即使技术上可行）：

- ❌ 任何 LLM provider 集成（OpenAI / Anthropic / Gemini / Ollama / ...）
- ❌ 任何 Agent loop / 多步推理 / 任务规划
- ❌ Compaction / Session 持久化 / 记忆
- ❌ Chromium 源码修改
- ❌ Chromium 编译流水线
- ❌ 安装包打包（dmg / msi / AppImage）
- ❌ 自动更新（OTA）— V0.1.3 再做
- ❌ Domain skills 包导入 — V0.1.1
- ❌ 远程浏览器（Browser Use Cloud） — V0.1.1
- ❌ Profile sync — V0.1.1
- ❌ heredoc 兼容模式（用户已确认不做）
- ❌ 评测框架（WebVoyager / Mind2Web） — V0.1.2 视情况

V0.1.0 的核心是 **薄、稳、跨平台、MCP 原生、可自迭代**。其他一切让位。

## 3. 技术栈决策与官方文档锚点

每条决策都有**官方文档依据**和**版本号锚定**，全部依据来自 2026-06-02 之前的官方资料。

### 3.1 运行时：Node.js 24 LTS "Krypton"

**版本**：`>=24.0.0 <25.0.0`，pin 到 LTS 线。  
**发布**：2025-05-06 → LTS 2025-10  
**EOL**：Active Support 至 2026-10，Security Support 至 **2028-04**  
**依据**：[endoflife.date/nodejs](https://endoflife.date/nodejs) 与 [nodesource.com/blog/nodejs-24-becomes-lts](https://nodesource.com/blog/nodejs-24-becomes-lts)

**为什么不是 22**：Node.js 22 "Jod" 的 active support 已于 2025-10-21 结束，仅剩 security support 到 2027-04。
**为什么不是 26**：Node.js 26 (2026-04 发布) 是 upcoming LTS，2026-10 才进入 LTS — V0.1.0 用 LTS 状态的版本更稳。
**为什么不是 Bun**：用户主力 Windows 开发，Bun 在 Windows 上仍在追赶 Node 的兼容性（虽然差距在缩小），稳定性优先。

### 3.2 语言：TypeScript 5.x strict

- `tsconfig.json` 启用 `"strict": true` + `"noUncheckedIndexedAccess": true` + `"exactOptionalPropertyTypes": true`
- 模块系统：**ESM**（Node 24 对 ESM 支持完善，`"type": "module"` + `.ts` 扩展名）
- 文件命名：**kebab-case**（与 BrowserOS 一致）

### 3.3 Schema 验证：Zod 4

**版本**：`zod@^4.0.0` (2025 年发布，目前 v4.0.1+)。  
**关键升级**：相对 Zod 3 有 **100x 的 TSC instantiation 减少**，TypeScript 编译速度大幅提升。  
**注意点**（来自 Zod 4 changelog）：
- `z.any()` 和 `z.unknown()` 在 object 里**不再隐式 optional**（默认行为变化）
- `z.array().nonempty()` 不再推断为 tuple，等同于 `z.array().min(1)`
- `z.discriminatedUnion` 现在支持 union/pipe 作为 discriminator

**与 MCP SDK 配合**（来自 SDK 官方文档示例）：

```typescript
import * as z from 'zod/v4';
server.registerTool('greet', {
  inputSchema: z.object({ name: z.string() })
}, async ({ name }) => {
  return { content: [{ type: 'text', text: `Hello, ${name}!` }] };
});
```

### 3.4 MCP SDK：`@modelcontextprotocol/sdk` v1.x

**协议版本**：MCP `2025-06-18`（截至 2026-06 的稳定 spec）。  
**SDK 包**：`@modelcontextprotocol/sdk@^1.x`（latest）。  
**导入路径**：`@modelcontextprotocol/sdk/server/mcp.js`、`@modelcontextprotocol/sdk/server/stdio.js`、`@modelcontextprotocol/sdk/server/streamableHttp.js`、`@modelcontextprotocol/sdk/types.js`。

**协议要点**（来自 [modelcontextprotocol.io/specification/2025-06-18/basic/transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)）：
- **两种标准 transport**：stdio 和 Streamable HTTP（已替代 2024-11-05 的 HTTP+SSE）
- **stdio**：subprocess + stdin/stdout JSON-line，stderr 仅日志，**stdout 必须只含合法 MCP 消息**（这条很重要——任何 `console.log` 都会污染协议）
- **Streamable HTTP**：单 endpoint 支持 POST（请求）+ GET（监听 SSE 流），用 `Mcp-Session-Id` header 管理会话，`MCP-Protocol-Version` header 协商版本
- **安全要求**：服务器**必须**校验 `Origin` header 防 DNS rebinding，本地必须只绑 `127.0.0.1`，**应**实现认证

### 3.5 IPC：原生 `node:net`，跨平台同代码

**API**：[`net.createServer()`](https://nodejs.org/docs/latest-v24.x/api/net.html#netcreateserveroptions-connectionlistener) + `server.listen(path)`。  
**Linux/macOS**：Unix domain socket — `/tmp/brisk-<name>.sock`（开机重启自动清理需 unlink 旧 socket）  
**Windows**：Named pipe — `\\\\.\\pipe\\brisk-<name>` 或 `\\\\?\\pipe\\brisk-<name>`（不持久化，进程退出自动清理）  
**关键文档原话**：

> On Unix systems, the path refers to a file system pathname for Unix domain sockets.
> On Windows, IPC uses named pipes. The path must be in the `\\?\pipe\` or `\\.\pipe\` format.

**架构性简化**：浏览器-harness 在 Windows 用 TCP loopback + 32 字节 token（因为 Python 标准库不支持 Windows named pipe）；**我们用 Node `net`，无需 token，跨平台同代码**。这是相对 browser-harness 的一个净改进。

### 3.6 CDP WebSocket：Node 内置 `WebSocket` (client) + `ws` 包做 keepalive

**Node 24 内置 WebSocket client**（globalThis.WebSocket，自 Node 21 起稳定，至 Node 22 取消 experimental flag），可以直接 `new WebSocket(url)`。
**为什么不用 puppeteer-core**：太厚，700KB+，绑定完整的 navigation graph、frame manager、target manager；我们要薄。  
**为什么不用 cdp-use**：那是 Python 库（browser-harness 用的）。  
**为什么不用 chrome-remote-interface**：是 callback 风格的老库，类型支持差。  
**结论**：自己包 50–100 行的 CDP client（参考 BrowserOS `cdp.ts` 设计模式），加 keepalive + 自动重连。

### 3.7 HTTP server：Hono + `@hono/node-server`

**版本**：`hono@^4.x` + `@hono/node-server@^1.x` + `@hono/mcp@^0.x`  
**为什么 Hono**：BrowserOS 用的就是 Hono（虽然他们用 Bun，但 Hono 自带 `@hono/node-server` 适配 Node）；轻、类型友好、跨运行时。  
**为什么不用原生 `node:http`**：路由 / middleware / CORS 都得自己写，没必要。  
**为什么不用 Express**：陈旧、ESM 兼容差、TypeScript 类型不友好。

#### 3.10.3 ⚠️ 重要修订：`node:sqlite` → `better-sqlite3`

原 §7.2.6 设计用 Node 24 内置的 `node:sqlite`。**校验后发现关键问题**：

> Node.js 的内置 SQLite 截至 2026 中期**未编译 `ENABLE_FTS5`**。任何 `CREATE VIRTUAL TABLE ... USING fts5(...)` 都会失败 `no such module: fts5`。
> 来源：[OpenClaw issue #62328](https://github.com/openclaw/openclaw/issues/62328)（同样的坑）

**因此 V0.1.0 改用 `better-sqlite3`**（npm 包）：
- 同步 API，比 `node:sqlite` 还快
- 默认编译 FTS5 + JSON1 + R-Tree
- v12+ 提供 Windows / macOS (x64 + arm64) / Linux (x64 + arm64) 预编译 binary，无需用户本地编译
- 唯一缺点：每次 Node 版本升级要确认预编译 binary 已发布

### 4.2 进程模型

Brisk V0.1.0 是**单进程 daemon**（一个 Node 进程同时承担 MCP server + IPC server + CDP client），可以多实例（按 `--instance <NAME>` 命名空间）。

**为什么单进程**：
- browser-harness 是 daemon + 一次性 client（client 通过 IPC 喂指令）。我们不需要这种分离——MCP client（如 Claude Code）本身就是长连接，stdio 子进程也是长连接，所以**进程本身就是 daemon**。
- 单进程降低复杂度（不需要 IPC 跨 daemon/client）。
- 多 MCP client 接同一个 Chrome 的场景，通过 Streamable HTTP server 共享一个 daemon 进程即可。

**进程启动两种模式**：

```bash
# 模式 A: stdio MCP server（被 MCP client subprocess 拉起）
brisk serve --transport stdio --cdp-port 9222

# 模式 B: Streamable HTTP MCP server（长驻，多 client 共享）
brisk serve --transport http --port 9100 --cdp-port 9222
```

### 4.3 数据流

**典型一次工具调用**（例：`click_at_xy`）：

```
1. MCP Client (e.g. Cursor)
       │  POST /mcp  { jsonrpc, method: "tools/call",
       │              params: { name: "click_at_xy",
       │                        arguments: {x: 100, y: 200} } }
       ▼
2. Hono server route → 校验 Origin → 校验 Session
       │
       ▼
3. MCP SDK Server.handleRequest → 调度到 tools/call handler
       │
       ▼
4. brisk-mcp/registry → 调用 click_at_xy.handler(args, ctx)
       │
       ▼
5. brisk-core/helpers/input.ts → clickAtXY(100, 200)
       │
       ▼
6. brisk-core/cdp/backend.ts → rawSend("Input.dispatchMouseEvent", { ... })
       │  WebSocket
       ▼
7. Chrome → 派发 mousePressed + mouseReleased
       │  WebSocket
       ▼
6. backend.ts → resolve pending promise
       ▼
5. helpers/input.ts → 返回（可选返回坐标）
       ▼
4. registry handler → response.text(`Clicked at (100, 200)`)
       ▼
3. MCP SDK → 包装为 ToolResult
       ▼
2. Hono → 响应 200 application/json 或 SSE
       ▼
1. MCP Client 接收
```

## 5. Monorepo 与模块设计

### 5.1 目录结构

```
brisk/                                  # ← 仓库根
├── packages/
│   ├── brisk-core/                     # CDP + helpers + daemon 核心（永远不动）
│   │   ├── src/

│   │   │   │   ├── backend.ts          # CdpBackend class（WS + keepalive + reconnect）

│   │   │   │   ├── profiles.ts         # PROFILES 路径配置（YAML 化）
│   │   │   │   └── types.ts            # CdpTarget, CdpSession types
│   │   │   ├── daemon/
```

```typescript
// packages/brisk-mcp/src/transports/http.ts
import { Hono } from 'hono';
import { serve } from '@hono/node-server';
import { StreamableHTTPServerTransport } from '@modelcontextprotocol/sdk/server/streamableHttp.js';
import { originCheck } from '../middleware/origin-check';

export async function startHttp(opts: { port: number; allowedOrigins: string[]; serverFactory: () => McpServer }): Promise<{ stop: () => void }> {
  const app = new Hono();

  app.use('*', originCheck(opts.allowedOrigins));

  app.post('/mcp', async (c) => {
    // 关键：每个请求新建 server + transport，防 ID collision 和状态污染
    // 这是 MCP SDK 1.26.0+ 的安全 fix GHSA-345p-7cg4-v4c7 的推荐做法
    const server = opts.serverFactory();
    const transport = new StreamableHTTPServerTransport({
      sessionIdGenerator: undefined,  // stateless mode
      enableJsonResponse: true,
    });
    await server.connect(transport);
    return transport.handleRequest(c.req.raw, c.req.body);
  });

  app.get('/mcp', (c) => {
    return c.json({ status: 'ok', message: 'POST to interact' });
  });

  app.get('/health', (c) => c.json({ status: 'ok' }));

  const server = serve({
    fetch: app.fetch,
    port: opts.port,
    hostname: '127.0.0.1',  // 关键：必须 127.0.0.1，不能 0.0.0.0
  });

  return { stop: () => server.close() };
}
```

## 6. MCP 工具规格

> **总计 37 个工具**：8 navigation + 6 observation + 9 input + 4 waits + 2 network + 3 admin + 5 skills = 37。

### 6.1 命名约定

- 全小写 `snake_case`（MCP 社区惯例，BrowserOS 也是）
- 动词在前：`click_at_xy`、`new_tab`、`wait_for_load`
- 参数也是 `snake_case`，但 zod schema 内部允许（MCP 自带映射）

### 6.2 通用 schema 元素

```typescript
const sessionParam = z.string().optional().describe('Target session ID; defaults to current attached page');
const targetIdParam = z.string().optional().describe('Specific CDP target ID');
```

### 6.3 完整工具表

#### 6.3.1 Navigation (8)

| Tool | 关键参数 | 行为 |
|---|---|---|
| `new_tab` | `url?: string` | 创建空白 tab，attach，然后 navigate（避免 createTarget+url 的 race） |
| `goto_url` | `url: string` | 在当前 attach 的 tab 导航 |
| `switch_tab` | `target_id: string` | `Target.activateTarget` + `attachToTarget`，设为 current |
| `close_tab` | `target_id?: string` | 默认关当前 |
| `list_tabs` | `include_chrome?: boolean` | 列出所有 page targets |
| `current_tab` | — | 当前 attached target 的 `{targetId, url, title}` |
| `ensure_real_tab` | — | 如果当前是 `chrome://` 或 omnibox-popup，自动 attach 到第一个真 tab |
| `iframe_target` | `url_substr: string` | 返回第一个 URL 包含 substring 的 iframe targetId |

**关键实现细节**：`new_tab` 必须先 `Target.createTarget({url: "about:blank"})`，再 `switch_tab`，再 `goto_url`——直接传 `url` 会因 race 让后续 `wait_for_load` 误判为已完成（browser-harness 源码注释里的血泪经验）。

#### 6.3.2 Observation (6)

| Tool | 关键参数 | 行为 |
|---|---|---|
| `capture_screenshot` | `full?: bool, max_dim?: number, path?: string` | `Page.captureScreenshot`，默认 max_dim=1800 防止 LLM 拒绝 |
| `page_info` | — | viewport + scroll + 文档尺寸；如果有 dialog，返回 `{dialog: {...}}` |
| `js` | `expression: string, target_id?: string` | `Runtime.evaluate`；自动包 IIFE（如果含 `return`） |
| `dom` | `selector?: string, depth?: number` | `DOM.getDocument` 或 `DOM.querySelector` |
| `drain_events` | — | 拉取自上次以来的所有 CDP 事件（fire-and-forget 缓冲） |
| `get_console_logs` | `since?: number` | 主动收集 console.* 消息（学 BrowserOS `console-collector.ts`） |

**关键实现**：`js` 工具需要解析表达式是否含 `return`，但**我们用更鲁棒的方式**——用一个 AST parser（`acorn`）做最小解析，或者干脆要求 agent 显式包 `() => {...}`，然后 wrap 成 `JSON.stringify((() => {...})())`。browser-harness 用 130 行手写状态机太脆。

#### 6.3.3 Input (9)

| Tool | 关键参数 | 行为 |
|---|---|---|
| `click_at_xy` | `x, y, button?, click_count?` | `Input.dispatchMouseEvent` mousePressed + mouseReleased（外加 mouseMoved 防 hover 状态污染，学 BrowserOS） |
| `type_text` | `text: string` | `Input.insertText` 批量塞文本 |
| `press_key` | `key: string, modifiers?: number` | `Input.dispatchKeyEvent` keyDown + char + keyUp（三段，学 browser-harness） |
| `scroll` | `x, y, dx?, dy?` | `Input.dispatchMouseEvent` mouseWheel |
| `fill_input` | `selector, text, clear_first?, timeout?` | JS focus + `Input` 系列 + dispatch synthetic events（让 React/Vue 监听器看到） |
| `dispatch_key` | `selector, key, event` | 在选定元素上 dispatch DOM `KeyboardEvent` |
| `upload_file` | `selector, path` | `DOM.setFileInputFiles` |
| `hover_at_xy` | `x, y` | `Input.dispatchMouseEvent` mouseMoved |
| `select_option` | `selector, value` | 找到 `<select>`，设置 value，dispatch change 事件 |

**关键实现细节（press_key）**：

```typescript
// 学 browser-harness helpers.py:253-262
// keyDown → 单字符额外发 char event → keyUp，三段都必要

await cdp.Input.dispatchKeyEvent({ type: 'keyDown', key, code, modifiers, ... });

await cdp.Input.dispatchKeyEvent({ type: 'keyUp', ... });
```

## 7. Skill 自学习机制（核心创新）

这是用户特别强调的需求，也是 Brisk 比 browser-harness 做得更好的关键点。本章详细设计。

### 7.1 browser-harness 现状（参考）

browser-harness 的"自学习"机制其实**非常简单**：

1. **agent_helpers.py 动态 import**：`helpers.py:_load_agent_helpers()` 会把 `agent-workspace/agent_helpers.py` 里所有非下划线开头的 public 函数 inject 到 `helpers` 命名空间。Agent 写一个函数 commit 进去，下次重新跑 daemon 就有了。
2. **domain-skills 是 markdown 文件**：`agent-workspace/domain-skills/<site>/*.md`，由 agent 在跑任务过程中观察到反直觉行为后**自己 PR**。已有 92 个站点。
3. **goto_url 后返回 skill 文件名**：`helpers.py:goto_url()` 在 `BH_DOMAIN_SKILLS=1` 时会返回该域名下的 skill 文件名列表（最多 10 个）。

**limitations**：
- 没有索引、没有 FTS 搜索，只能精确 hostname 匹配
- 没有失败日志机制，agent 写不写 skill 全靠 prompt 引导
- agent_helpers.py **必须重启 daemon** 才能生效（动态 import 但是是启动时一次性的）
- 没有 versioning（agent 改坏了就改坏了）

#### 7.2.3 自动注入：`_meta.domain_skills`

每次 `goto_url` / `new_tab` 后，工具响应的 `_meta` 字段自动含有该域名的 skill 概要：

```typescript
// 伪代码 (brisk-mcp/src/tools/navigation.ts)
export const goto_url = defineTool({
  name: 'goto_url',
  handler: async (args, ctx, response) => {
    await ctx.daemon.gotoUrl(args.url);
    response.text(`Navigated to ${args.url}`);
    // ✨ 自动注入相关 skill
    const skills = await ctx.skills.findByUrl(args.url, { limit: 5 });
    if (skills.length > 0) {
      response.meta('domain_skills', skills.map((s) => ({
        name: s.name,
        title: s.title,
        tags: s.tags,
        uri: `mcp://brisk/skill/${s.domain}/${s.name}`,
      })));
      response.meta('skill_hint',
        `${skills.length} skills available for ${new URL(args.url).hostname}. ` +
        `Call read_skill or fetch the URIs above before attempting a task.`
      );
    }
  },
});
```

这样 agent 在 navigate 后**自动**看到 "你有 3 个关于 github.com 的 skill 可用"，主动调用 `read_skill`——**结构性比 prompt 引导可靠**。

#### 7.2.6 数据库 schema

```sql
-- agent-workspace/skills.db (SQLite)

CREATE TABLE IF NOT EXISTS skills (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  domain      TEXT NOT NULL,                    -- e.g. "github.com"
  name        TEXT NOT NULL,                    -- e.g. "repo-actions"
  title       TEXT NOT NULL,
  tags        TEXT NOT NULL DEFAULT '[]',       -- JSON array
  content     TEXT NOT NULL,
  created_at  INTEGER NOT NULL,                 -- unix ms
  updated_at  INTEGER NOT NULL,
  based_on    TEXT,                             -- failure_id
  UNIQUE(domain, name)
);

CREATE VIRTUAL TABLE IF NOT EXISTS skills_fts USING fts5(
  domain, name, title, tags, content,
  content='skills',
  content_rowid='id'
);

-- 自动同步触发器
CREATE TRIGGER skills_ai AFTER INSERT ON skills BEGIN
  INSERT INTO skills_fts(rowid, domain, name, title, tags, content)
  VALUES (new.id, new.domain, new.name, new.title, new.tags, new.content);
END;

CREATE TRIGGER skills_au AFTER UPDATE ON skills BEGIN
  UPDATE skills_fts SET domain=new.domain, name=new.name, title=new.title, tags=new.tags, content=new.content WHERE rowid=new.id;
END;

CREATE TRIGGER skills_ad AFTER DELETE ON skills BEGIN
  DELETE FROM skills_fts WHERE rowid=old.id;
END;

-- 失败记录（独立表）
CREATE TABLE IF NOT EXISTS failures (
  id          TEXT PRIMARY KEY,                 -- "f-12345"
  domain      TEXT NOT NULL,
  action      TEXT NOT NULL,
  expected    TEXT,
  observed    TEXT,
  root_cause  TEXT,
  workaround  TEXT,
  tags        TEXT NOT NULL DEFAULT '[]',
  created_at  INTEGER NOT NULL,
  resolved_by_skill TEXT                        -- 后续写了 skill 的话，记录 skill id
);
```

**SQLite 库选择**：Node 22+ 内置了 `node:sqlite`（experimental），Node 24 稳定。直接用：

```typescript
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync('./agent-workspace/skills.db');
```

不需要 better-sqlite3 等外部依赖了，这又是一个简化。

### 8.4 为 V0.3 Chromium 嵌入预留的契约

当我们写自家 Chromium fork 时，需要 Chromium C++ 代码能 spawn brisk daemon 并管它的生命周期。参考 BrowserOS `browseros_server_manager.cc` 的设计，brisk daemon **必须**支持以下命令行参数（V0.1.0 就实现，作为契约）：

```bash
brisk serve \
  --transport http \                  # stdio 或 http
  --port <N> \                        # HTTP 端口
  --cdp-port <N> \                    # CDP 连接端口（Chromium 启动时已知）
  --cdp-ws <URL> \                    # 或直接给 WebSocket URL
  --instance <NAME> \                 # 多实例命名空间
  --workspace <PATH> \                # agent-workspace 位置
  --runtime-dir <PATH> \              # IPC + pid 文件位置
  --log-dir <PATH> \                  # 日志位置
  --health-path <PATH> \              # 默认 /health
  --allowed-origin <ORIGIN> \         # Streamable HTTP 安全
  --version                            # 输出版本然后退出
```

**生命周期信号**：
- `SIGTERM` → 优雅退出（关闭 CDP，关闭 HTTP，返回 0）
- `SIGINT` → 立即退出（返回 non-zero）
- HTTP `POST /shutdown` → 优雅退出，由 Chromium C++ 在浏览器关闭时调用

**Health endpoint**：`GET /health` 返回 `{ status: "ok", uptime: <ms>, version: "..." }`，Chromium 30 秒一次轮询。

**OTA 钩子**：HTTP `POST /update?version=<v>` 触发自我更新（V0.1.3 实现）；V0.1.0 返回 501 Not Implemented。

这些参数和端点**在 V0.1.0 就实现到位**，即使现在没人调用，是为了避免未来改契约。

## 9. 安全模型

### 9.1 Streamable HTTP transport 安全（MCP 规范明确要求）

引用 [MCP 2025-06-18 spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)：

> 1. Servers MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks
> 2. When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)
> 3. Servers SHOULD implement proper authentication for all connections

**Brisk 实现**：

```typescript
// packages/brisk-mcp/src/middleware/origin-check.ts
import { createMiddleware } from 'hono/factory';

const DEFAULT_ALLOWED_ORIGINS = new Set([
  'http://localhost',
  'http://127.0.0.1',
  'http://[::1]',
  'null',  // file:// 或 sandbox 来源
  'vscode-webview://*',
  'cursor-webview://*',
]);

export function originCheck(extra: string[] = []) {
  return createMiddleware(async (c, next) => {
    const origin = c.req.header('origin');
    if (!origin) {
      // 没有 Origin 通常是非浏览器客户端（curl / claude desktop），允许
      return next();
    }
    const allowed = new Set([...DEFAULT_ALLOWED_ORIGINS, ...extra]);
    const ok = [...allowed].some((pattern) => {
      if (pattern.includes('*')) {
        const prefix = pattern.split('*')[0];
        return origin.startsWith(prefix);
      }
      return origin === pattern || origin.startsWith(pattern + ':');
    });
    if (!ok) return c.text(`Origin not allowed: ${origin}`, 403);
    return next();
  });
}
```

**默认 bind 127.0.0.1**，命令行不允许 `--host 0.0.0.0`（必须 `--allow-remote` 显式打开，且伴随警告 + 强制认证 token）。

### 9.2 stdio transport 安全

stdio 没有网络面，但要注意：
- **任何 `console.log` 都会污染 stdout**（MCP 协议要求 stdout only 含 JSON-RPC 消息）。**V0.1.0 启动时立刻把全局 `console.log` 重定向到 stderr**：

```typescript
// brisk-mcp/src/transports/stdio.ts
function redirectStdoutToStderr() {
  // 关键：所有 logger 必须用 stderr
  const origLog = console.log;
  console.log = (...args) => process.stderr.write(args.join(' ') + '\n');
  // 同样 console.info, console.debug
  // console.error / warn 已经在 stderr，不动
}
```

### 9.3 工具安全

学 MCP 规范的 Tool Safety 原则：
- Tool description 是不可信的——任何 prompt injection 都可能在里面
- Host 必须显式同意才能 invoke tool（MCP client 负责）
- Brisk 这边的责任：不在 tool description 里嵌入 instruction 给 host 端 LLM

### 9.4 文件系统访问

- `write_skill` 只能写 `agent-workspace/` 内
- `attach_helper` 只能写 `agent-workspace/agent_helpers.ts`
- `upload_file` 接收的路径必须 exists 且可读，不允许写

### 9.5 网络访问

- `http_get` 默认走 Node `fetch`，**不连接外部 API**
- `goto_url` 在 V0.1.0 不限制 URL（agent 决定）
- 不暗自走代理/cloud（browser-harness 有 fetch-use 默认走 proxy，**我们不要**——避免用户被无端代理）

## 10. 跨平台细节

### 10.1 Windows（用户主开发环境）

| 议题 | 方案 |
|---|---|
| IPC | Named pipe `\\\\.\\pipe\\brisk-<name>` |
| Chrome 路径 | `%LOCALAPPDATA%\Google\Chrome\User Data` 等 |
| 进程发现 | `tasklist /FI "IMAGENAME eq chrome.exe"` |
| 用户数据目录 | `%LOCALAPPDATA%\Brisk` |
| 临时目录 | `os.tmpdir()` → `%TEMP%` |
| stdio 子进程编码 | UTF-8（设置 `process.stdout.setEncoding('utf-8')`） |
| Chrome 144+ Allow popup | 检测到失败时打开 `chrome://inspect/#remote-debugging` 并提示用户 |
| --remote-debugging-port=9222 启动 | brisk chrome 子命令包好 |

### 10.2 macOS

| 议题 | 方案 |
|---|---|
| IPC | Unix socket `/tmp/brisk-<name>.sock` |
| Chrome 路径 | `~/Library/Application Support/Google/Chrome` 等 |
| 进程发现 | `ps -A -o comm=` |
| 用户数据目录 | `~/Library/Application Support/Brisk` |
| Chrome 启动 | `open -a "Google Chrome" --args --remote-debugging-port=9222 --user-data-dir=...` |

### 10.3 Linux

| 议题 | 方案 |
|---|---|

## 12. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| Chromium 升级 Chrome 149+ 改变 CDP 行为 | 中 | 中 | 跟随 BrowserOS 的 Chromium 版本（148），并在 CDP backend 加版本检测 |
| Windows named pipe 在 WSL / Docker 跨边界场景失败 | 中 | 中 | V0.1.0 不支持 WSL/Docker 跨边界，文档明确；V0.1.x 加 TCP 兜底（带 token） |
| MCP SDK API 在 1.x 内变化 | 低 | 中 | pin 具体小版本，CI 检测 SDK 升级 |
| 用户 Chrome 装的是 Snap 包 | 中 | 高（连不上） | `brisk doctor --fix-snap` 给出明确替换指引 |
| Chrome 144+ Allow popup 反复弹 | 中 | 中 | 文档明确指引切换 Way 2（独立 profile + `--remote-debugging-port`） |
| LLM 不会主动调用 `record_failure` / `write_skill` | **高** | **高** | 不仅靠 prompt，还在工具 description 里强调（"You SHOULD call record_failure ..."），并在 tool error 响应里自动建议 |
| stdio MCP 的 `console.log` 污染协议 | 中 | 高 | 启动时立刻重定向 stdout → stderr，并加单元测试验证 |
| Node 24 内置 sqlite 仍 experimental（截至 2026-06） | 低 | 低 | 准备 fallback 到 `better-sqlite3`（编译开销） |
| pnpm workspace 在 Windows 路径过长 | 低 | 低 | 仓库根目录尽量短，文档建议 `C:\dev\brisk` |
| 用户改坏了 `agent_helpers.ts` 导致 daemon 启动失败 | 中 | 中 | `workspace/loader.ts` try/catch，失败时退回到空 + log warning，agent 知道发生了什么 |

## 附录 C — 术语表

| 术语 | 含义 |
|---|---|
| **Brisk** | 本项目名 |
| **Harness** | "马具"，比喻 LLM 控制浏览器的薄连接层。来自 browser-harness |
| **CDP** | Chrome DevTools Protocol — Chromium 调试协议 |
| **MCP** | Model Context Protocol — LLM 标准化集成协议 |
| **stdio transport** | MCP 用 stdin/stdout 通信的方式（subprocess 模式） |
| **Streamable HTTP transport** | MCP 用单 HTTP endpoint 通信的方式（POST 请求 + GET SSE） |
| **IPC** | Inter-Process Communication — 本项目用 unix socket / named pipe |
| **Way 1** | 用户已开 Chrome + chrome://inspect 勾 checkbox 启用 CDP 的连接方式 |
| **Way 2** | 用 `--remote-debugging-port=9222 --user-data-dir=<path>` 启动独立 Chrome 实例 |
| **Daemon** | 长驻进程。Brisk V0.1.0 中 daemon 与 MCP server 是同一个进程 |
